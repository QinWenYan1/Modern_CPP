# 逐篇交付学习笔记

## 确认本轮要交付什么

先读用户当前要求、[项目约定](../../STATE.md)和[当前计划](../../PLAN.md)，再打开对应笔记及相邻知识点的最新正文。读者问一句“这里为什么这样写”时先解释；要求草稿时在聊天展示；已经同意写入的，直接在约定位置修改。整章规划和用户本轮授权分别核对。

沿用[根 README 的小节笔记生成指南](../../../README.md)和[仓库约定](../../../AGENTS.md)。环境有 `course-notes-generator` 时可用它生成基础结构。其他机器直接按仓库里的指南工作即可。

## 组织一个知识点

1. 先写出读者学完能回答的具体问题，用标题点明结论。第一点的开头承接篇题或前一篇；之后每一点的第一段接住上一步，说清原办法解决了什么、现在换了哪个条件。并列主题可以从共同问题引入。
2. **把承接放在新知识点标题下面。** 例如先承认 `packaged_task` 已经能保存函数返回值，再问“如果工作函数还要继续运行，怎样先交出已经准备好的结果？”。这样读者带着问题去看 `promise` 的例子。
3. 讲例子时先交代谁在做什么，从能看懂的最小例子开始。写清关键对象从哪里来、哪一步得到结果，以及它怎样回答开头的问题。需要对照多个线程的先后顺序时，再加入简短示意图。完成后遮住示例，只读标题和首段，检查读者能否理解本点为何出现。
4. **核实旧知识点的去向。** 对照受保护的旧笔记，检查已采用的概念、原例和警告在新篇何处得到解释。需要移动、重编号、改标题或改原文时，逐篇列出位置、原文、拟改内容和理由，请用户批准。只发现原文问题时登记到[问题账本](../../AUDIT.md)，报告相应验收项“待确认”。

## 核查与交付

检查本篇计划的全部主题、编号和目录锚点、相邻知识点的衔接、总结和考试速记。核对文件名与一级标题括号内的完整英文篇名。对比本轮差异，保留用户自己的批注和已批准范围以外的正文。第 17 章在第九步集中处理各级 README；届时可复用 `chapter-nav-readme` 和 `course-root-readme`，也可直接按仓库现有导航核对。

单篇交付报告包含四项。

- **本次交付**写明文件、知识点数量、新增和保留范围、已批准的旧文调整。
- **实际材料**按[逐知识点来源核对](../trace-note-sources/SKILL.md)交付聊天报告和内部记录。
- **验收结果**逐项说明主题覆盖、技术核对、原文保护、格式与链接、来源追溯，使用“通过／待确认／未完成”，注明实际核查范围。
- **待申请的修改**列出需用户决定的原文和理由，或写“无”。在[当前计划](../../PLAN.md)记下这篇的停点和下一项已授权行动。
